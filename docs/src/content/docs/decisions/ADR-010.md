**Status**: Decided

## Context

The default deployment fronts the SPA and `/api` with oauth2-proxy ([ADR-006](../adr-006/)). The proxy authenticates a person against the app's Keycloak realm and forwards the request to the app over the pod's loopback interface, with the person's identity in `X-Forwarded-Email` and `X-Forwarded-Preferred-Username`. A person's rights ([ADR-011](../adr-011/)) and their name on every commit ([ADR-013](../adr-013/)) both need that identity inside the app.

Three facts bound how far the headers can be trusted. The proxy sets them from the session on the routes it authenticates, and strips any a client sent; on the routes it skips (`/mcp` and `/api/health`) it passes the client's headers through untouched. The app's port is reachable inside the cluster without passing the proxy. And uvicorn, by default, rewrites the request's peer from `X-Forwarded-For` when the hop is loopback, so a forwarded address could pass for the sidecar's.

## Decision

- The app trusts the forwarded identity only when the TCP peer is loopback (`127.0.0.1` or `::1`), the request carries the proxy secret, the path is not on the machine door, and the deployment runs behind the proxy (`STUDIO_AUTH_SCOPE=mcp`). The secret (`STUDIO_PROXY_SECRET` in the app's auth Secret) reaches the proxy as `OAUTH2_PROXY_BASIC_AUTH_PASSWORD`, and with `--pass-basic-auth` the proxy sends it as the password of the Basic header it sets on every request it authenticates. Loopback alone proves only that the caller is inside the pod, and the gates run the corpus's own code there ([ADR-011](../adr-011/)); the secret proves it is the sidecar. With no secret configured, no forwarded identity is trusted. One `X-Forwarded-Email` shaped like an email names the person; the preferred username is their display name, the email when absent. A value that could break a commit's author line (control characters, `<`, `>`) names nobody.
- The server runs with `--no-proxy-headers`, so the peer it reports is the real one. The chart passes `--pass-user-headers=true` to the proxy explicitly.
- From any other peer, on `/mcp`, or malformed, the headers act as nobody. Reads stay open to the proxy's gate as before; a write with nobody behind it answers 401.
- Standing alone (`STUDIO_AUTH_SCOPE=all`), the app's HTTP Basic gate covers the human door, and its holder acts as the service, the studio's own identity, with the authority of the deployment.

## Rationale

The sidecar is the only party that has verified the person. The loopback check keeps the rest of the cluster out, independent of network policy; the secret, which only the sidecar holds, keeps out every other process in the pod; and refusing the headers on the skipped routes closes the one path where the proxy forwards a client's own values.

## Consequences

- `/api/me` answers who the browser acts as; the SPA renders the identity chip and every control from it.
- A request that reaches the app's port directly reads like an anonymous visitor and writes nothing.
- The release needs `STUDIO_PROXY_SECRET` in the app's auth Secret and the chart that hands it to the proxy; until both are in place, people read and nobody writes on the human door.
- The stand-alone deployment keeps one actor, the service, as before.

## Alternatives considered and rejected

- **Validating the ID token in the app**: a second OIDC client in the app for a fact the sidecar already established, with its own keys and expiry to manage.
- **Trusting the headers from any peer**: any pod in the cluster could write as anyone.
