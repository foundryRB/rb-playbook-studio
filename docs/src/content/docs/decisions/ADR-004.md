**Date**: 2026-07-03
**Status**: Decided

## Context

Agents (Claude Code sessions and other MCP-capable clients, on any machine) need the studio's capabilities: load REFs and skills, run validation, make gated edits. The studio already exposes these capabilities through inbound ports consumed by the REST adapter and the SPA.

## Decision

The MCP server is a third inbound adapter, mounted at `/mcp` on the same FastAPI application using streamable HTTP. Tools mirror the inbound ports one-to-one; write tools exist wherever the composition wires write use cases. Client-side effects follow the client-executes idiom: the server owns its datastore, and effects on the calling machine ship as content the agent executes with its own hands (a skill install returns the skill's files; the agent writes them to its runtime directory).

## Rationale

- One shared core means every MCP write goes through the identical gate-validate-rollback-commit path as the SPA and REST; trust calibration is enforced in one place.
- Deriving the tool list from the capability wiring keeps the deployed and local instances honest about what they expose, with zero mode branches.
- An MCP server can never write the client's filesystem, and does not need to: returning content for the agent to apply is the correct division of ownership.

## Alternatives considered and rejected

- **A separate MCP service** in front of the REST API: a second system with its own auth, deployment, and drift surface, wrapping capabilities the hexagon already exposes as ports.
- **Server-side skill installation**: impossible across the MCP boundary (the server has no access to the client machine) and undesirable even locally, since it hides an effect the agent should own.
