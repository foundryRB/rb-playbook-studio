**Status**: Decided

## Context

A team shares one playbook. It needs people who only read, people who own particular skills, agents, MCP or RAG cards, people responsible for a galaxy, and admins. Two doors write to the same corpus: the human door ([ADR-010](../adr-010/)) and the machine door ([ADR-012](../adr-012/)). Who may change what has to be one answer, held where the corpus lives, so it is versioned and reviewed with the content it governs.

## Decision

**One file.** `OWNERS` at the playbook root, in CODEOWNERS syntax: a path anchored at the root, then the owners, named by the email their sign-in carries. A path is literal (no wildcards); a trailing slash is optional.

```text
/                                 admin@example.com
/galaxies/craft/                  writer@example.com
/galaxies/craft/skills/x/         owner@example.com other@example.com
not-before someone@example.com 2026-10-01
```

**The rule.** A person may change a path a line gives them, or anything under it. Rights are the union of every line that names the person: a narrower line never takes away what a wider one gives. That reads as four roles:

| Role | Owns | May |
| --- | --- | --- |
| admin | `/` | everything: the playbook page, `OWNERS` itself, push and refresh |
| galaxy writer | `galaxies/<name>/` | the galaxy's page, its REFs and every atom in it; creates atoms there, naming their owners |
| atom owner | one skill folder, agent, MCP or RAG card | edits it, a new file in its skill included; creates nothing |
| reader | nothing | reads everything; their agents read and their writes refuse |

**One function.** `may(actor, action, path)` decides, with four actions: edit, create, administer (`OWNERS`, push, refresh) and validate (running the gates on demand, open to any role that writes). Every write use case calls it with its target before it touches the corpus, so both doors give the same answer; a refusal names the role that would allow the act (HTTP 403, or a tool error). The service ([ADR-012](../adr-012/)) holds the deployment's authority.

**Read from the corpus.** The studio reads `OWNERS` from the clone it serves, again whenever its text changes, so a merged or pulled edit takes effect on the next request with no restart. Each document read carries `can_edit` for the reader, and `/api/me` names their role, the galaxies they may create in and the atoms they own; the SPA renders its controls from those and never reads `OWNERS` itself.

**Edited by an admin, refused when wrong.** An edit through either door that does not parse, or names a path the playbook does not hold, is refused before anything is written; a valid one is gated and committed like every edit. A creation that names owners adds their line to `OWNERS` in the same transaction.

**Fail closed.** With no `OWNERS`, or one that does not parse, nobody owns anything and every person is a reader. An install's `OWNERS` lands in its playbook before the studio release that reads it.

**Revocation.** `not-before <email> <date>` refuses the personal tokens issued to that person before the date (UTC midnight) or ISO timestamp.

**Code the gates run stays inside its owner's rights.** The playbook's suite runs code the corpus carries, skill scripts among it, written by their owners. The boundary is the operating system's: the runtime image creates an unprivileged `gates` user (`STUDIO_GATES_USER`), and the gates judge a copy of the clone that leaves out its git directory, owned by that user and run as it without supplementary groups, in an environment that carries none of the studio's `STUDIO_` settings. The managed clone is closed to every user but the studio's own (mode `0700`), and the studio's process environment is unreadable to another user, so that code can neither change the clone a write commits, by any path, nor read the remote's credential or the studio's keys. Every process the gates user still runs is ended when the gates finish. A gates user that cannot be resolved fails the gates instead of running them as the studio. The forwarded identity needs the proxy's secret, not only a loopback peer ([ADR-010](../adr-010/)), so that code cannot speak for a person to the app either. The scaffolders and the back-link sync run without the studio's settings too.

## Rationale

CODEOWNERS is the syntax a reviewer already reads, and putting the file in the corpus makes every rights change a reviewed, attributed commit. Literal paths keep the rule decidable by reading one line at a time; union semantics keep an atom owner's line from accidentally demoting the admin above it. Deciding in the use cases rather than the adapters is what makes both doors agree.

## Consequences

- The file names people by email, so an install's `OWNERS` is its own and does not travel between installs' playbooks.
- An admin who removes their own `/` line through the studio can restore it only through git.
- A rule naming a path that is later deleted grants nothing until the path returns; edits through the studio refuse such a rule.
- What the boundary leaves: code the gates run as the `gates` user can still reach the network and read what any user in the image can read; it can make the verdict of the run it is part of pass or fail, which the gates' own outcome already exposes to its owner. A scaffolder (the maker's `bootstrap-*` skills) runs as the studio inside the clone, because creating a planet writes there, so the owners of those scaffolder skills hold the studio's power for the length of a creation. A local run, with no gates user named, runs the gates as the operator.

## Alternatives considered and rejected

- **Roles from Keycloak groups**: rights would live outside the corpus, unreviewed beside the content they govern, and could not name a single skill.
- **GitHub's last-match semantics**: an atom owner's line would take the atom away from its galaxy writer and the admin.
- **Glob patterns**: a rule a reader cannot evaluate by eye, for a corpus whose layout is already a tree of literal paths.
