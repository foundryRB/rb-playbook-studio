## Context

A connector-only session synced the toolchain over the per-skill path: enumerate the graph, then `get_skill_files` per skill and `get_agent_files` per agent, writing each file by hand. For the current corpus that is about 84 tool calls and roughly a million tokens, every byte passing through the model twice, and an interrupted run leaves a skill half-written. The work is mechanical: copy what differs and report a table. The client-executes idiom ([ADR-004](../adr-004/)) holds; the cost is in the model doing the copying.

Three facts constrain the shape. The shell that runs a command is not the connector, so it holds no credential, and the command lands in a transcript. The default deployment fronts every path except `/mcp` and `/api/health` with oauth2-proxy for humans ([ADR-006](../adr-006/)). The rules for where skills and agents land, and what a prune may remove, already live in the playbook's `scripts/install_skills.py`, and the studio serves agent renderings by loading that file ([ADR-004](../adr-004/), playbook INT-TOOL-002).

## Decision

The MCP door gains `get_install_command(runtime)`. It returns one line per shell family: `curl -fsSL '<host>/mcp/install/<token>/install.sh?runtime=<r>' | sh -s --` for POSIX shells, and `& ([scriptblock]::Create((irm '<host>/mcp/install/<token>/install.ps1?runtime=<r>')))` for PowerShell. Flags append to either.

- **Credential.** The token is minted per call by the door: an HMAC over its expiry with a per-process random key, valid for ten minutes. The gate admits it only on `GET` requests under `/mcp/install/`; it opens no MCP call and no REST route. The connector's Basic credential never appears in the line.
- **Path.** The install routes live under `/mcp/install/`, where machine credentials already pass: oauth2-proxy skips `/mcp`, and the application's own gate admits the token there. No gateway, chart, or platform change is involved.
- **Bundle.** `GET /mcp/install/<token>/bundle.tar.gz?runtime=<r>` returns one gzipped tar: a manifest (a digest over the files, and per file its path, sha256, and the installer option naming its directory), every skill file as its folder's bytes and executable bit, every agent rendered for that harness by the same use case `get_agent_files` serves, the playbook's `install_skills.py` from the same revision, and the applier.
- **One implementation.** The install scripts only find Python 3.8 or newer, download, unpack, and run the applier. The applier, `apply_bundle.py`, is standard-library Python and the only place the write happens: it compares by hash and, on POSIX, by executable bit, stages each differing skill whole beside its target and renames it in, replaces agent files atomically, deletes nothing without `--prune`, and prints one summary table with a restart note when anything changed. It loads the bundled installer for the harness set, each harness's agents-directory option and default directory (`install_hint`), and the OpenCode default (`opencode_agents_default()`). Every prune decision is the installer's own: `_prune()` removes skills, and what it and the agent prune inside `_install_agents()` would remove is found by running them on an empty shadow of each directory. Two facts the installer's `main()` holds and publishes nowhere else are restated: the skills directory default (`~/.claude/skills`) and that the OpenCode option resolves through `opencode_agents_default()`. A test runs the installer and the applier over the same machine and compares what is left; it needs a playbook checkout, which CI does not have.

`get_skill_files` and `get_agent_files` stay, for fetching a single skill or agent.

## Rationale

One download and one script turn the sync into a single shell call whose only output the model reads is the table. A minted, download-only token keeps a leaked line worth downloads of the toolchain for ten minutes, where the Basic credential would be worth the whole door. Placing the routes where the machine credential already passes keeps the change inside this repository. Writing the logic once in Python, and loading the playbook installer for every rule it publishes, keeps one home for the rules a clone install and a connector install share; Python is already what the toolchain's own scripts run on.

## Consequences

- The client needs Python 3.8 or newer, for the applier and for the installer code it executes; a test runs both under 3.8 where that interpreter is supplied. PyYAML is optional: the bundled installer imports it to render agents, and the bundle carries agents rendered; where it is missing the applier stands an empty module in for it.
- A token admits any number of downloads until it expires, and dies with the process that minted it; a restart retires every outstanding line, and the caller asks for a fresh one.
- The two restated facts, and each harness's `install_hint` standing for its agents default, are held equal to the installer only where a playbook checkout is present. A change to either in the playbook surfaces when that test runs against it, not in this repository's CI. Publishing both from the installer would let the applier load them too.
- The bundle carries a binary skill asset as its bytes. The per-skill path carries text, so for such a file the two differ; the bundle matches the local installer.

## Alternatives considered and rejected

- **The Basic credential in the command**: publishes the door's long-lived credential into every transcript that runs a sync.
- **Routes under `/api`**: behind oauth2-proxy, so a machine request would need a proxy skip rule in the chart.
- **The write logic in both `install.sh` and `install.ps1`**: two copies of the hash, stage, and swap rules to keep equal, one of them untestable on the Linux runners.
