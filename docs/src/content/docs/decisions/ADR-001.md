**Date**: 2026-07-03
**Status**: Decided

## Context

The studio is the read-write central management surface for the private `playbook` repository. The deployment needs the content available to the pod, and the content changes through the studio itself.

## Decision

The pod clones `playbook` onto a PersistentVolumeClaim on first start, pulls to stay at head, and pushes accepted edits. The image carries application code only, never content. Argo CD pins the app version; the content is application data whose version tracking, audit trail, and merge semantics are git itself.

## Rationale

- A read-write central source makes baked snapshots stale by design: the studio's own edits would immediately outdate its image.
- Runtime pull deletes all cross-repo CI machinery (content-change dispatch, pin-bump commits, content rebuilds) that a baked snapshot would require.
- GitOps purity is preserved where it matters: the app's version is pinned and reconciled; the datastore versions itself.

## Alternatives considered and rejected

- **Bake content into the image at CI**, with a `repository_dispatch` pin-bump pipeline keeping it fresh: correct for a read-only viewer, wrong for a writing surface (see stale-by-design above), and it carries heavy cross-repo CI machinery.
- **Host the studio inside `playbook`**: co-locating manager and managed creates a self-redeploy loop, where every content push rebuilds and redeploys the manager that made the edit. It also collides with that repo's genericity rule (an onboarded app repo necessarily carries instance-specific hostnames and deploy pins) and with its `intent.yaml`, which holds the playbook's own claims. Manager and managed must be separate repos.
- **Keep the studio inside `csd-library`**: a public library monorepo is the wrong home for an application whose purpose is rendering a private repo, on both the visibility and the packaging axis.
