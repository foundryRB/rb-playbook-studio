**Date**: 2026-10-08
**Status**: Decided

## Context

An inner loop is how one agent session iterates on one task: stages, the writes each stage may make, back edges with a required cap, and a `done` that a command's exit status decides. It has to hold in a developer's own harness (Claude Code, OpenCode) and in an unattended worker pod alike, where nothing can stop to ask. Prompt text cannot refuse a write or cap a retry, so the loop needs an engine that tracks the stage and checks every tool call against it.

An open-source engine that does this was sought before building one, in October 2026.

## Decision

The loop engine is built here.

- Loops are playbook content beside skills and agents, served by this studio over its door and in its install bundle, and versioned with the playbook revision.
- The engine is a small runtime the playbook carries as a skill: a stage tracker (current stage, iterations per back edge, the `done` command), a hook the harness calls before every tool call, and a local UI it serves on localhost, where a person manages their own loops, the ones the playbook installed, the ones they imported, and the current project's, in one place. The UI is static files and a small local server, with no build step.
- `install-playbook` installs it and registers its hook in the harness settings wherever the harness has hooks; with no loop chosen, the hook allows everything.

## Rationale

No project found covers stages with per-stage write rules, capped back edges and a command-decided `done`, enforced at the tool call, for both harnesses, unattended. The pieces that exist each cover one part, at a maturity the delivery line cannot rest on. Keeping loops and their engine in the playbook gives them the corpus's gates, its revision pin and its install path with no new component to run.

## Alternatives considered and rejected

- **Cupcake (EQTY Lab)**: a policy layer in the harness hook path, Apache-2.0, OPA/Rego compiled to WebAssembly, for Claude Code, Cursor, Factory and OpenCode. It enforces policies but has no notion of a staged loop; it calls itself an early preview, published no tagged release, documents a Nix-only install, and does not state its failure mode.
- **GitHub Spec Kit and OpenSpec**: spec-driven workflows (specify, plan, tasks, implement) delivered as slash commands and skills. They guide the agent and enforce nothing; their verify step is the thinnest part.
- **Claude Code's Ralph plugin**: re-feeds a prompt from a stop hook under a `--max-iterations` cap. One stage, no write rules.
- **LangGraph and Temporal**: engines for agent programs written against them, which do not constrain a harness session.
- **Community hook sets** (flow-state, agentic-os and similar): each one author's workflow, without a schema, releases or a second harness.
