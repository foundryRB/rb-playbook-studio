**Date**: 2026-07-03
**Status**: Decided

## Context

Gated edits mutate the working clone on the PVC. The studio needs a persistence discipline for accepted edits and a publishing model toward the content repo's `main`.

## Decision

Every edit that passes validation becomes a local commit immediately, with a conventional message and the authenticated editor recorded. A deliberate push action publishes accumulated commits. A push rejected because upstream moved triggers `pull --rebase` and a retry; a real conflict surfaces as HTTP 409 listing the conflicting files, with no automatic resolution.

## Rationale

- Commit-per-edit means nothing lives only in dirty working-tree state; an accepted edit is always a recoverable git object.
- The PVC persists unpushed commits across pod restarts.
- The UI shows the unpushed count and diff, so publishing is an informed decision rather than a side effect.
- Surfacing conflicts raw keeps the trust boundary honest: the gates decide what enters the corpus, a human decides how history reconciles.

## Alternatives considered and rejected

- **Push per edit**: couples every accepted edit to network availability and upstream state, and turns a burst of small edits into a burst of pushes; accumulation with a deliberate publish matches how a person works.
- **Working-tree-only edits with a commit-and-push button**: leaves accepted edits as uncommitted state that a crash or restart can lose, and makes the audit trail depend on operator discipline.
- **Automatic conflict resolution**: any heuristic silently rewrites corpus content; a 409 with the file list is the honest failure.
