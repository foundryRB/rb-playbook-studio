## Context

One working tree serves every door. HTTP writes, MCP write tools and the content poll each touch it, on different threads. A commit names one person ([ADR-013](../adr-013/)), so it must hold exactly that person's change: two writes interleaving in one tree would commit each other's edits under the wrong name, and a pull landing mid-validation would change what the gates judge.

A gated write also runs the playbook's whole validation suite. A handler that runs it on the event loop holds every other route for its length, the health check included, and the kubelet probes readiness every 10 seconds and liveness every 30, so a long validation can take the studio out of rotation or restart it mid-write.

## Decision

- **One lock.** A process-wide re-entrant lock, held by the corpus guard with the rights ([ADR-011](../adr-011/)), spans each write's whole transaction: the rights check again under the lock, the edit, the regeneration, the validation, the rollback or the commit. Push, refresh, the poll (the service refreshing the clone) and the on-demand validation take the same lock, and the install bundle reads under it for a consistent snapshot. Re-entrancy lets a push that reconciles with a pull hold it once.
- **The rights check runs before waiting too,** so a refused write never queues behind a long validation.
- **Off the loop.** HTTP write routes are plain handlers, which FastAPI runs on worker threads; MCP write tools run their use case with `anyio.to_thread`. The event loop only routes, so `/api/health` answers within its probe timeout while a validation runs.

## Rationale

The corpus is one git working tree; a single lock is the smallest serialisation that makes every commit coherent, and the studio's writes are rare and human-paced, so serialising them costs nothing a person would notice. Reads take no lock and stay concurrent.

## Consequences

- Writes queue behind one another; a long validation delays the next write, never a read or the health check.
- The lock is per process. Several writers would need a shared lock; the deployment runs one replica with a `Recreate` strategy.

## Alternatives considered and rejected

- **A lock per document**: the gates read the whole corpus, and a write regenerates sections in REFs it never named.
- **A write queue with a worker**: the same serialisation with a second moving part and a caller that has to poll for its own result.
